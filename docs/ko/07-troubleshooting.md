# 장애 대응 기록

이 문서는 운영 장애보고서 원문이 아니다. 실제 사건에서 내부 이름, 주소, 로그와 설정값을 빼고, 내가 확인한 순서와 판단만 남겼다. 확인하지 못한 원인은 확정해서 쓰지 않는다.

## 1. 토큰 갱신 지연이 FCM 발송 504로 이어진 문제

### 보였던 현상

서버 기동 직후에는 정상인데 access token 만료 주기가 가까워지면 발송 504가 나타나고 점차 늘었다.

### 처음 확인한 것

- Nginx timeout
- Redis 조회 지연
- FCM 자체 오류
- 단말 토큰 문제
- 외부 네트워크 상태

증상만으로 결론이 나지 않아 발송 흐름에 구간별 시간을 추가했다.

### 확인된 원인

FCM 호출은 정상 범위였지만, 그 직전의 외부 OAuth token 발급이 오래 걸렸다. 발송 요청 안에서 token을 갱신하던 구조 때문에 OAuth 지연이 공통 API에서 연계 API와 Java/데이터 전달 구간을 거쳐 앞단 timeout으로 이어졌다. 만료 순간 여러 요청이 동시에 갱신을 시도해 호출이 더 몰릴 수 있었다.

### 바꾼 내용

1. FCM access token을 Redis에 저장
2. 발송 요청과 선제 갱신을 분리
3. 두 공통 API 인스턴스의 갱신 시점을 분산
4. 프로세스 안 Promise single-flight 추가
5. 인스턴스 사이 Redis 기반 갱신 조정 추가
6. 기동 확인, 정기 갱신, 만료 감시, 긴급 복구 경로 구성

외부 OAuth 실패 자체가 바로 사라진 것은 아니지만, 유효 token이 남아 있는 동안 발송 요청으로 지연이 번지는 것을 줄였다.

## 2. 애플리케이션을 보완해도 토큰 갱신 실패가 다시 늘어난 문제

### 보였던 현상

토큰 갱신 방어 로직이 있는데도 외부 OAuth timeout이 평소보다 늘고, 연속 실패 뒤 실제 token 만료 위험이 나타났다.

### 조사 순서

```text
공통 API 컨테이너
→ 내부 프록시 경로
→ WEB 계층
→ 외부 OAuth
```

같은 요청을 호스트와 컨테이너에서 각각 확인했다. 성공 응답과 특정 시간에 잘리는 timeout이 두 갈래로 나타났고, 애플리케이션 timeout보다 앞에서 HTTP 504가 만들어지는 점을 함께 봤다.

### 확인된 원인

외부 통신 정책이 바뀌어 컨테이너에서 OAuth로 나가는 경로가 불안정해진 것이 확인됐다.

### 역할을 나눠 기록

- 내가 한 일: 구간별 조사, 애플리케이션 재시도·기존 token 유지·감시·운영 확인 기능 보완
- 네트워크 담당이 한 일: 외부 통신 정책 수정

애플리케이션 보완은 영향을 흡수했고, 네트워크 조치는 원인을 제거했다. 두 작업을 섞어 내 성과로 적지 않는다.

## 3. 두 인스턴스 로그가 같은 파일에 섞인 문제

### 보였던 현상

공통 API A와 B의 로그 집계가 거의 완전히 같아, 알고 있는 실행 시점과 맞지 않았다.

### 범위를 좁힌 방법

파일 크기와 해시를 비교하고 인스턴스별로 달라야 하는 로그 특성을 확인했다. 두 파일은 사실상 같은 데이터였고, 로그 안에서 손상 흔적도 발견됐다.

### 확인된 원인과 조치

두 컨테이너가 공유 스토리지의 같은 로그 파일에 동시에 기록하고 있었다.

- 인스턴스별 경로로 분리
- 로그에 인스턴스 식별값 추가
- 이중화를 이용해 한 대씩 순서대로 적용

이 사건에서 가장 크게 남은 것은 “코드로 설명되지 않는 로그가 보이면 코드 가설만 늘리지 말고, 그 로그가 만들어지는 경로부터 확인한다”는 기준이었다.

## 4. 서버 재기동 뒤 Redis가 살아나도 공통 API가 복구되지 않은 문제

### 보였던 현상

정기 서버 작업 뒤 공통 API 프로세스는 실행 중인데 발송 관련 요청은 503을 계속 반환했다. 두 인스턴스가 같은 증상이었고, Redis 관련 작업에서 연결 종료 오류가 보였다.

### 확인된 원인

공통 API가 Redis보다 먼저 시작해 초기 연결에 실패했고, Redis client가 제한된 재시도 뒤 연결 재시도를 중단했다. Redis가 나중에 정상화돼도 애플리케이션 내부 연결은 자동으로 살아나지 않았다. 공통 API를 다시 시작하면 바로 복구되는 점으로 확인했다.

### 적용한 방향과 현재 공개 범위

- 개별 Redis 명령의 빠른 실패와 연결 재시도를 분리
- 연결은 backoff를 두고 계속 재시도
- `connect`, `ready`, `close`, `reconnecting`, `end` 상태를 구분해 기록

코드 수정과 개발환경 확인까지 완료한 기록을 기준으로 적었으며, 운영 반영과 실제 서버 작업 재현 검증은 이 문서에서 완료됐다고 주장하지 않는다.

## 공통으로 지킨 조사 방식

1. 증상과 원인을 같은 것으로 두지 않는다.
2. 서비스 전체 시간보다 구간별 시간을 먼저 나눈다.
3. 두 인스턴스가 함께 실패하면 공통 의존성을 본다.
4. 애플리케이션 방어와 인프라 원인 제거를 구분한다.
5. 로그와 지표가 구조와 맞지 않으면 수집 경로를 검증한다.
6. 확인되지 않은 원인은 `unknown`으로 남긴다.
