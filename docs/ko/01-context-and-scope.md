# 정리 배경과 공개 범위

## 왜 이 문서를 다시 썼나

이 저장소의 출발점은 새 시스템 설계가 아니다. 실무에서 이미 만들고 운영한 FCM 알림 경로를 이직 준비 과정에서 다시 설명할 필요가 생겼다.

처음 v1을 만들 때는 회사 정보를 지우는 데 신경을 많이 썼다. 그 결과 실제 서비스 순서까지 사라지고, 내가 봐도 “내가 만들었던 구조가 맞나?” 싶은 일반론이 남았다. v2에서는 방향을 바꿨다.

> 회사 정보를 숨기는 것과 실제 경험을 지우는 것은 다르다.

그래서 서비스명과 설정값은 공개하지 않되, 실제 기술과 서비스 경계, 운영 중 겪은 문제와 판단 순서는 그대로 남겼다.

## 공개 문서에서 사용하는 이름

| 한국어 | English | 의미 |
|---|---|---|
| 기존 업무 서비스 | Legacy business service | 알림 요청이 시작되는 기존 업무 영역 |
| Java / 데이터 전달 | Java / data handoff | 기존 업무 요청 데이터를 연계 API로 전달하는 구간 |
| 연계 API | Integration API | Java/데이터 전달 구간의 요청을 받아 발송 데이터를 정리하고 공통 API로 넘기는 NestJS 구간 |
| 공통 API | Common API | 이중화로 운영하며 FCM 호출과 access token 갱신을 담당한 NestJS 구간 |
| DB Repository | DB Repository | 수신 대상과 단말 토큰을 조회하는 데이터 접근 구간 |
| 발송 | send / delivery | 서버가 FCM에 메시지를 요청하고 결과를 기록하는 일 |
| 토큰 갱신 | access-token refresh | FCM 호출에 필요한 access token을 새로 받는 일 |
| 단말 토큰 | device token | FCM이 단말을 식별할 때 사용하는 등록값 |

실제 내부 이름을 이런 일반적인 말로 바꿨을 뿐, 별도의 추상 컴포넌트를 새로 만들어 실제 구조인 것처럼 설명하지 않는다.

## 실제 흐름과 직접 담당 범위

```text
기존 업무 서비스
  → Java / 데이터 전달
  → 연계 API (NestJS)
  → 공통 API (NestJS, 이중화)
  → FCM
  → Flutter 단말
```

내가 직접 다룬 핵심은 Java/데이터 전달 이후의 서버 발송 구간이다.

- NestJS 연계 API와 공통 API의 발송 흐름
- DB Repository를 통한 수신 대상·단말 토큰 조회
- Redis를 이용한 access token, badge 상태, `messageId` 발송 상태, 토큰 갱신 조정
- `messageId`를 이용한 E2E 로그 연결과 중복 요청 처리
- 다수 대상 병렬 발송과 개별 실패 격리
- FCM access token 갱신과 장애 복구
- `UNREGISTERED` 단말 토큰 처리
- Grafana/Loki를 이용한 모니터링과 로그 분석
- 운영 장애 조사와 애플리케이션 측 보완

기존 업무 서비스와 Flutter 앱은 E2E 흐름에 포함되지만, 이 저장소에서는 그 내부 구현 전체를 내 소유 범위로 잡지 않는다. 특히 Flutter의 수신 화면, 앱 내부 badge 처리, 단말 토큰 재등록 구현은 서버 발송 구조와 구분한다.

## 운영 중 실제로 문제였던 것

FCM 요청을 한 번 보내는 코드는 어렵지 않았다. 운영하면서 시간이 많이 들었던 것은 다음이었다.

1. access token 만료 시점에 외부 OAuth 호출이 발송 요청을 붙잡고 504까지 이어진 문제
2. 공통 API 두 인스턴스가 같은 token을 동시에 갱신하려는 문제
3. 다수 대상을 순차 발송하면서 지연이 계속 누적된 문제
4. 한 건의 실패가 배치 전체 실패로 번질 수 있던 문제
5. `UNREGISTERED`와 실제 시스템 장애가 같은 실패 숫자에 섞인 문제
6. 여러 인스턴스의 로그가 같은 경로에 섞여 분석 근거 자체를 믿기 어려웠던 문제
7. 프로세스는 떠 있지만 Redis 연결은 복구되지 않아 API가 계속 실패하던 문제

문서는 이 순서대로 “무엇이 있었는지 → 어떻게 범위를 좁혔는지 → 무엇을 바꿨는지 → 어디까지 확인했는지”를 적는다.

## 공개하지 않는 것

- 회사·조직·센터·내부 시스템의 실제 이름
- 운영 API 경로와 요청 원문
- 호스트명, IP, VIP, 방화벽 규칙과 네트워크 주소
- 실제 Redis key와 운영 시간·TTL·재시도 횟수 같은 설정값
- credential, access token, service account, private key
- 운영 로그 원문, 사용자 정보, 단말 식별정보, 민감 payload
- 회사 소스코드와 전체 topology

수치도 경험을 설명하는 데 꼭 필요하지 않다면 공개하지 않는다. 예제 값은 모두 가상값이다.

## AI를 사용한 범위

문서 구조화, 문장 다듬기, Mermaid 다이어그램, 영문 번역에는 AI를 활용했다. 사실관계, 기술 판단, 장애 대응 순서와 담당 범위는 실제 업무 기록을 기준으로 다시 검토했다.

이 기준은 단순한 고지가 아니라 문서를 쓸 때의 제한이다. 원래 구현에 없던 서비스를 추가하거나, 아직 검증하지 않은 개선을 완료된 결과처럼 쓰지 않는다.
