# 토큰 갱신을 발송 요청에서 분리

## 상황

발송 요청 중 FCM access token을 새로 받는 구조에서 외부 OAuth 지연이 공통 API의 504로 이어졌다. Redis cache를 추가한 뒤에도 만료 시점의 동시 갱신이 남았다.

## 판단

정상 발송은 Redis의 유효한 access token을 사용한다. 갱신은 서버 기동 확인, 선제 갱신, 만료 위험 감시, 긴급 복구 경로에서 처리한다.

한 프로세스에서는 진행 중인 Promise를 공유하고, 두 인스턴스 사이에서는 Redis 기반으로 갱신을 조정한다.

## 선택의 대가

- 갱신 경로가 늘어나 서로 겹치지 않게 관리해야 한다.
- 기존 token을 유지할지, 언제 긴급 복구할지 운영 기준이 필요하다.
- Redis와 외부 OAuth 상태를 각각 모니터링해야 한다.
- 애플리케이션 보완이 네트워크 원인 자체를 고친 것으로 오해하면 안 된다.

## 공개 제한

실제 갱신 주기, 만료 임계값, 재시도 간격과 횟수, Redis lock 값은 공개하지 않는다.
